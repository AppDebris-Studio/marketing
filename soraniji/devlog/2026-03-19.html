Firebase Cloud Functions Security Rules iOS パフォーマンス セキュリティ

Firebase 認証・Security Rules・Cloud Functions 層にわたる9つの脆弱性・パフォーマンス問題を 一気に修正した日。帳簿アプリの脆弱性診断で得た知見を SoraNiji に応用し、 セキュリティレビューで特定した CRITICAL/HIGH 課題を全て解決。 特に batch overflow と account takeover リスク の修正が重要。

1. Firebase 認証の孤児化問題（P0 #1）

SoraNiji は匿名UUID方式を採用している——Firebase Auth の anonymous UID は Keychain の UUID とは別の識別子で、アプリ再インストール時に UID が変わる。 すると Firestore の auth_uid フィールドが古い UID に紐づいたまま残り、 以降のすべての操作でセキュリティ検証失敗で投稿・いいねが機能しなくなる。

これが「auth_uid 孤児化」の問題だ。

問題の危険性

  • アプリ再インストール後、ユーザーが投稿・いいねできない（サイレント失敗）
  • 旧 auth_uid が Firestore に無限に残る（dead data 蓄積）
  • Firebase Auth の無効化上限に引っかかる（個人アカウントで数百件の limit）

Cloud Function: relinkAuthUid

新規 Cloud Function relinkAuthUid を実装。iOS から呼び出して auth_uid を新しい値に一括更新する。 

// Dev/backend/src/relinkAuthUid.ts の主要ロジック
export const relinkAuthUid = functions
  .https.onCall(async (data, context) => {
    // ✅ App Check + Auth 検証
    if (context.app == undefined) throw new HttpsError('failed-precondition', '...');
    if (!context.auth) throw new HttpsError('unauthenticated', '...');

    // ✅ UUID 形式検証（RFC 4122）
    const UUID_REGEX = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
    if (!userUuid || !UUID_REGEX.test(userUuid)) {
      throw new HttpsError('invalid-argument', 'user_uuid must be a valid UUID');
    }

    // ✅ アカウント乗っ取り防止
    // 呼び出し者の auth_uid が既に別ユーザーに紐づいている場合は拒否
    const callerExisting = await db
      .collection('users')
      .where('auth_uid', '==', newAuthUid)
      .limit(1)
      .get();
    if (!callerExisting.empty) {
      throw new HttpsError('permission-denied', 'Caller auth_uid already linked');
    }

    // ✅ Batch 処理（450 件ごとに分割）
    let batch = db.batch();
    let opCount = 0;

    batch.update(userRef, { auth_uid: newAuthUid });
    opCount++;

    const postsSnap = await db
      .collection('posts')
      .where('user_uuid', '==', userUuid)
      .get();

    for (const postDoc of postsSnap.docs) {
      batch.update(postDoc.ref, { auth_uid: newAuthUid });
      opCount++;
      if (opCount >= 450) {
        await batch.commit();
        batch = db.batch();
        opCount = 0;
      }
    }
    if (opCount > 0) await batch.commit();

    // ✅ Auth user 削除（Firestore 更新が成功した後に実行）
    if (shouldDeleteOldAuth && currentAuthUid) {
      try {
        await admin.auth().deleteUser(currentAuthUid);
      } catch {
        // 削除失敗は非致命的
      }
    }
  });

🔐 重要な設計判断 3 つ：
  1. Batch overflow 防止: Firebase の 500 項目制限を避けるため 450 で分割。Auth user 削除を commit 後に実行し、データ不一致を防止
  2. Account takeover 検証: 呼び出し者の auth_uid が別ユーザーに既に紐づいていないか確認（既知の乗っ取り手法を対策）
  3. Anonymous-only check: 旧 auth_uid のユーザーが匿名のみか検証。非匿名ユーザーの削除は拒否

2. Firestore Rules 強化（P0 #2–3）

2-1. like_count >= 0 ガード

いいね数が負数になる可能性があった。トランザクション内で race condition が起きると、 increment(-1) が複数回実行されて -1, -2, ... になる。 

// firestore.rules
match /posts/{postId} {
  allow update: if
    request.auth.uid == resource.data.auth_uid &&
    request.resource.data.like_count >= 0;  // ← 追加
}

2-2. internal subcollection 所有権検証

posts/{id}/internal/location に誰でもアクセスできてしまう脆弱性があった。 

// firestore.rules
match /posts/{postId}/internal/location {
  allow create: if
    // 投稿が存在し、呼び出し者の auth_uid と一致
    exists(/databases/$(database)/documents/posts/$(postId)) &&
    get(/databases/$(database)/documents/posts/$(postId)).data.auth_uid == request.auth.uid;
}

3. Storage Rules 強化（P0 #3）

認証なしでアップロード可能だった問題を修正。 さらに SVG インジェクション対策として、MIME type を制限。 

// storage.rules
match /{allPaths=**} {
  allow read: if true;
  allow write: if
    request.auth != null &&
    request.resource.contentType.matches('image/(jpeg|png|heic|heif|webp)') &&
    request.resource.size < 5 * 1024 * 1024;  // 5MB
}

4. iOS deletePost → Cloud Function 経由（P0 #4）

クライアント側からの Firestore updateData() 直接呼び出しをやめ、 Cloud Function 経由に変更。サーバー側で Storage 削除と likes クリーンアップを 一括処理する。 

// SoraNijiIOS/PostRepository.swift
func deletePost(postId: String) async throws {
  let _ = try await FirebaseManager.shared.functions
    .httpsCallable("deletePost")
    .call(["postId": postId])
}
✅ これにより Security Rules で deletePost を forbidden にできる （管理者の削除はサーバー側のみに限定）

6. FCM 冪等性（P1 #2）

Cloud Functions の at-least-once 配信特性により、 同じイベント ID で onPostCreate が複数回実行される可能性がある。 結果、同じユーザーへ 2 回以上プッシュ通知が送信される。

対策: _idempotency ドキュメント

// onPostCreate.ts の冪等性ガード
const eventId = context.eventId;
const idempotencyRef = db.doc(`_idempotency/onPostCreate_${eventId}`);
const existing = await idempotencyRef.get();
if (existing.exists) {
  functions.logger.warn('[onPostCreate] duplicate event skipped', { postId, eventId });
  return;  // 重複実行をスキップ
}

// 処理を続ける...
await idempotencyRef.set({
  createdAt: admin.firestore.FieldValue.serverTimestamp(),
  expireAt: admin.firestore.Timestamp.fromDate(expireAt),  // TTL
});

7. タイムゾーンバグ修正（P1 #3）

天気データの取得で、クライアント（UTC）とサーバー（Open-Meteo が timezone=auto で返すローカル時刻）の 時刻フォーマットが異なり、マッチしていなかった。

修正前（UTC ベース文字列比較 — バグ）

// toISOString() は UTC を返す
const postedAtStr = new Date().toISOString();  // "2026-03-19T15:00:00Z"
// Open-Meteo は timezone=auto で返す：時刻配列は "2026-03-20T00:00" (JST)
// ↓ マッチしない…

修正後（ミリ秒ベース nearest-neighbor）

// onPostProcess.ts
const timeParsed = time.map((t) => new Date(t).getTime());
const result = [];
for (const offset of [-2, -1, 0, 1, 2]) {
  const targetMs = postedAt.getTime() + offset * 3600 * 1000;
  // 最も近い時刻のインデックスを探す（30分以内なら一致とみなす）
  let bestIdx = -1;
  let bestDiff = Infinity;
  for (let i = 0; i < timeParsed.length; i++) {
    const diff = Math.abs(timeParsed[i] - targetMs);
    if (diff < bestDiff) {
      bestDiff = diff;
      bestIdx = i;
    }
  }
  if (bestIdx === -1 || bestDiff > 30 * 60 * 1000) continue;
  result.push({
    offset_hours: offset,
    condition: toWeatherCondition(weathercode[bestIdx]),
    temp_celsius: Math.round(temperature_2m[bestIdx] * 10) / 10,
  });
}
✅ タイムゾーン問題をロバストに解決。JST/UTC ズレを自動吸収

10. 本日の教訓まとめ

  • Batch overflow 防止: Firebase 500 項目制限を避けるため 450 で分割。CLI エラーメッセージを見落とさない
  • Account takeover 防止: auth_uid 再リンク時に「既に別ユーザーに紐づいているか」を検証
  • Anonymous-only check: providerData の配列長でチェック。デフォルト拒否の姿勢が重要
  • Internal subcollection の所有権: get() で親ドキュメントを検証して初めて安全
  • N+1 クエリ削減: whereField(in:) で 30 件ずつまとめて fetch
  • FCM 冪等性: eventId + _idempotency ドキュメントで at-least-once を制御
  • タイムゾーン問題: 文字列ベース比較は危険。ミリ秒基準で nearest-neighbor
  • TTL ポリシー: 時系列データは自動削除の仕組みを最初から用意すること
