iOS Capability 設定の修正と
位置情報プライバシーの強化

Expo Config Plugin iOS EAS Build Firebase App Check プライバシー

App Store 提出を前に見落としていた重大バグを2件修正した日。aps-environment が development にハードコードされたまま本番ビルドを出すと、プッシュ通知が完全に機能しない。 また、生 GPS 座標を Firestore に保存することへのプライバシーリスクを指摘し、 クライアント側で 111m 単位に丸める対策を入れた。

1. iOS Capability 設定の監査

今日は Capability 設定（entitlements・app.json・eas.json）を一通り確認した。 Gemini と Codex に並列で分析を依頼したところ、以下の問題が見つかった。

項目重大度現状対応
aps-environment🔴 CRITICALdevelopment 固定Config Plugin で動的設定
appattest-environment🟠 HIGHentitlements に欠落production 限定で追加
UIBackgroundModes🟡 MEDIUMプラグイン任せ確認済み（自動注入）
NSMicrophoneUsageDescription🟢 LOW欠落Phase 7 動画対応前に追加
⚠️ 最重要: aps-environment=development のまま App Store 提出すると、 FCM プッシュ通知が本番で完全サイレント失敗する。Geohash ベース通知（コア機能）が無効になる。

2. Expo managed workflow と $(APS_ENV) 変数問題

最初に考えた対策は、Xcode のビルド変数 $(APS_ENV) を entitlements に書く方法だった。 ところが Expo managed workflow ではこれが機能しない。

理由は npx expo prebuild を実行するたびに entitlements ファイルが再生成されるため、 Xcode のビルド変数は prebuild 時点では評価されないからだ。 さらに expo-notifications プラグインが既存の aps-environment を検知して 上書きをスキップする挙動も確認した（if (!config.modResults['aps-environment']) の条件分岐）。

結論: Config Plugin 方式が唯一の永続的解決策。

3. withApsEnvironment.js の実装

EAS Build が自動設定する EAS_BUILD_PROFILE 環境変数を読み取り、 entitlements を動的に生成する Config Plugin を新規作成した。 

// plugins/withApsEnvironment.js
const { withEntitlementsPlist } = require('@expo/config-plugins');

const withApsEnvironment = (config) => {
  return withEntitlementsPlist(config, (config) => {
    const profile = process.env.EAS_BUILD_PROFILE || 'development';
    const apsEnv = profile === 'production' ? 'production' : 'development';

    config.modResults['aps-environment'] = apsEnv;

    // appattest-environment は production のみ設定
    // （ローカル開発用 Provisioning Profile に capability 不要）
    if (profile === 'production') {
      config.modResults['com.apple.developer.devicecheck.appattest-environment'] = 'production';
    }
    return config;
  });
};

module.exports = withApsEnvironment;

app.json の plugins 配列の末尾に追加した。 expo-notifications の後に実行することで、プラグインが設定した値を確実に上書きできる。 eas.json への追記は不要——EAS が EAS_BUILD_PROFILE を自動設定してくれる。

検証結果

$ EAS_BUILD_PROFILE=production npx expo prebuild --clean --platform ios
$ cat ios/SoraNiji/SoraNiji.entitlements

<string>production</string>
<key>com.apple.developer.devicecheck.appattest-environment</key>

production で正しく生成されることを確認した ✅

4. 位置情報プライバシーの強化

投稿フロー（app/post/input.tsx）から src/api/posts.ts を経由して Firestore の posts/{id}/internal/location に保存される lat_raw/lng_raw を確認した。

これまでは生 GPS 座標（精度 < 10m）をそのまま保存していた。 Firestore の Security Rules でクライアントからのアクセスは遮断しており、 Cloud Functions（Admin SDK）のみが読み取れる設計だが、 高精度データを保持すること自体がリスクとの判断で丸め処理を追加した。

フィールド丸め単位精度用途
lat_raw（修正後）0.001°≈ 111minternal のみ・通知計算用
lat_fuzzy0.05°≈ 5.5km公開ドキュメント・地図表示用
 
// src/api/posts.ts — internal/location 書き込み前
const round1m = (v: number) => Math.round(v * 1000) / 1000;
tx.set(db.collection('posts').doc(postId).collection('internal').doc('location'), {
  lat_raw: round1m(req.lat_raw),
  lng_raw: round1m(req.lng_raw),
  created_at: firestore.FieldValue.serverTimestamp(),
});

通知半径の最小値は数 km 単位なので、111m の誤差は実用上問題ない。 仕様書（01_data_models.md v0.6、05_non_functional.md v0.2）にも丸めポリシーを明記した。

5. 本日の教訓まとめ

  • $(APS_ENV) 変数は Expo managed workflow では使えない。Config Plugin 一択
  • expo-notifications プラグインは既存値を上書きしない——必ず末尾に自前プラグインを置く
  • EAS Build は EAS_BUILD_PROFILE を自動設定する。eas.json への手動追記は不要
  • appattest-environment をローカル開発用に追加すると Provisioning Profile 不一致でクラッシュする
  • Security Rules で遮断済みでも、高精度データを保持しないことがプライバシーの原則
  • 位置情報の丸め精度は「通知半径の最小値に対して誤差が小さいか」で決める
