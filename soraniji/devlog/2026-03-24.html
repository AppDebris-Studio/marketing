認証を全面刷新 — 匿名認証廃止、Sign in with Apple のみに

Apple Sign-In Firebase Auth Cloud Functions アカウント削除 App Store

SoraNiji の認証方式を根本から刷新した。これまでの「匿名認証 + Keychain UUID」方式を全廃止し、 Sign in with Apple を唯一の認証方式にした。 同時に App Store Review Guideline 5.1.1(v) で必須のアカウント削除機能も実装。 1日で認証基盤と削除パイプラインの両方を完成させた。

なぜ匿名認証を廃止したのか

匿名認証は「登録不要ですぐ使える」UX を提供していたが、複数の問題があった：

  • Keychain 喪失 = アカウント完全消失 — 端末リセットや機種変更で UUID が失われると、ユーザーの投稿やいいねが孤児化する
  • relink_token インフラの複雑さ — UUID と Firebase UID のマッピングを維持するために relinkAuthUid、initRelinkToken、setUserUuidClaim の3つの Cloud Functions が必要だった
  • App Store 審査要件 — アカウント作成機能があるアプリは、アプリ内からアカウント削除を開始できる機能が必須。匿名認証だと「誰のアカウントを削除するか」が曖昧になる

Apple Sign-In なら Firebase UID が Apple ID に紐づくため、端末を変えてもアカウントが復元できる。 しかも空スコープ（requestedScopes: []）でメールも名前も取得しないので、 プライバシーファーストの方針は維持できる。

Phase 1: 認証基盤の書き換え

AppleSignInCoordinator

ASAuthorizationController を使った Apple Sign-In フローを実装。 nonce は SecRandomCopyBytes で生成し、SHA-256 でハッシュ化してリクエストに付与。 scope は空で、メール・名前・電話番号は一切要求しない。 

let request = ASAuthorizationAppleIDProvider().createRequest()
request.requestedScopes = []  // 空スコープ — 個人情報なし
request.nonce = sha256(nonce)

AuthIdentityManager

旧: signInAnonymously() → 新: signInWithApple()。 AppleSignInCoordinator から OAuthCredential を受け取り、Auth.auth().signIn(with:) で Firebase Auth にサインイン。 signOut() も追加。

AppState

AuthState に .unauthenticated を追加。 起動時に Auth.auth().currentUser をチェックし、 既存セッションがあれば復元、なければサインイン画面へ遷移。 UUIDManager / RelinkTokenManager への依存を完全に削除。

RootView

サインイン画面を新設。Apple 純正の SignInWithAppleButton を使い、 利用規約・プライバシーポリシーへのリンクも配置。 旧 authFailed 画面（オフライン時）は削除。

UserRepository

ドキュメント ID を Keychain UUID から Firebase UID に変更。 relink ロジック（30行超）を全削除し、シンプルな存在チェック + 作成/更新に。 auth_provider: "apple" を設定。

Phase 2: アカウント削除

App Store Review Guideline 5.1.1(v) への準拠。削除フローは10ステップ：

#ステップ実装場所
1設定画面から削除操作を開始SettingsView
2最終確認ダイアログconfirmationDialog
3-4Sign in with Apple で再認証AppleSignInCoordinator
5Apple トークン revokedeleteAccount.ts
6-8Firestore + Storage + 関連データ削除deleteAccount.ts
9Firebase Auth ユーザー削除AuthIdentityManager
10ローカルキャッシュ削除 + サインアウトAuthIdentityManager

Apple トークン Revoke の仕組み

削除時にクライアントが authorizationCode を取得し、Cloud Function に送信。 サーバー側で Apple の auth/token エンドポイントで refresh_token に交換し、 auth/revoke で失効させる。 これにより Apple 側でもユーザーのトークンが無効化される。 

// Cloud Function: Apple token revocation
const tokenRes = await fetch("https://appleid.apple.com/auth/token", {
  method: "POST",
  body: new URLSearchParams({
    client_id: APPLE_CLIENT_ID,
    client_secret: clientSecret,  // JWT signed with .p8 key
    code: authorizationCode,
    grant_type: "authorization_code",
  }),
});
const { refresh_token } = await tokenRes.json();

await fetch("https://appleid.apple.com/auth/revoke", {
  method: "POST",
  body: new URLSearchParams({
    client_id: APPLE_CLIENT_ID,
    client_secret: clientSecret,
    token: refresh_token,
    token_type_hint: "refresh_token",
  }),
});

廃止したもの

  • signInAnonymously() — Firebase 匿名認証
  • UUIDManager — Keychain UUID 生成・永続化
  • RelinkTokenManager — relink_token の Keychain 管理
  • relinkAuthUid Cloud Function — UUID-UID 再リンク
  • initRelinkToken Cloud Function — トークン初期化
  • setUserUuidClaim Cloud Function — カスタムクレーム設定

3つの Cloud Functions と2つの Keychain マネージャーが不要に。 認証コードの総行数は大幅に削減され、保守性が向上した。

本日の教訓

  • シンプルさは正義 — 匿名認証の「手軽さ」は relink_token 等の複雑なインフラで支えられていた。Apple Sign-In のみにすることで、認証レイヤー全体が劇的にシンプルに
  • 空スコープでプライバシー維持 — requestedScopes: [] で個人情報を一切取得しない。Apple Sign-In = 個人情報収集ではない
  • 削除は設計初期に — App Store Guideline 5.1.1(v) のアカウント削除要件は後付けだと大変。認証方式の刷新と同時に実装するのが正解
  • Apple token revoke は authorizationCode が鍵 — クライアントから authorizationCode を取得し、サーバー側で refresh_token に交換→revoke する2段階が必要
